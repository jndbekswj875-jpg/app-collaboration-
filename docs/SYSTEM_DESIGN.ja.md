# システム設計：コミュニティAIワークスペース

**英語版：** [English version](SYSTEM_DESIGN.md)  
**状況：** 共同開発に向けた設計案です。実装済みのシステムではありません。

## システムの全体像

```text
スマートフォン・パソコンのブラウザ
       ↓
Webアプリ（招待・プロフィール・チャット・共有ボード）
       ↓
バックエンド（認証・グループ権限・API）
       ├─ メッセージ保存用データベース
       ├─ グループごとのリアルタイム配信
       ├─ タスク・決定事項・出欠管理
       └─ AI接続サーバー
             ├─ 最初は OpenAI API または Claude API
             └─ 将来的に自前のオープンウェイトモデルも比較
                    ↓
            AIが下書きを作成
                    ↓
            人が確認・修正・承認
                    ↓
            共有ボードに確定反映
```

## 最初の完成目標

招待された2人が別々のブラウザでログインし、同じ非公開グループでリアルタイムにメッセージを送受信できること。更新しても履歴が残り、共有ボード上のタスクを変更できます。招待されていない人は会話を閲覧できません。その後、AIで承認待ちの提案を作る機能を試します。

## 必要な機能

| 機能 | 内容 | 実装順 |
| --- | --- | --- |
| 認証 | 安全なログインとセッション管理 | 最初 |
| グループ招待 | 招待リンク、期限、メンバー権限 | 最初 |
| リアルタイムチャット | メッセージ送信・保存・同期・エラー表示 | 最初 |
| 共有ボード | タスク・決定事項・未解決の質問 | 最初 |
| AIアシスタント | 必要な会話から要約やタスクの下書きを作る | 次に検証 |
| 出欠確認 | 参加・未定・不参加と変更履歴 | チャット検証後 |
| プロフィール | 自己紹介、SNS、公開範囲 | 最初は最小限 |
| コミュニティ投稿 | お知らせ、思い出、写真 | 需要が確認できたら |
| 会費・決済 | 会費記録、将来は外部決済サービス | 需要が確認できたら |

## データの構造案

- `users`：ログインに必要なアカウント情報。
- `profiles`：表示名、自己紹介、興味、任意のSNSリンク、公開範囲。
- `groups`：グループ名、管理者、公開設定。
- `group_members`：誰が参加し、どの権限を持つか。
- `invitations`：招待先、期限、招待用の安全なトークン。
- `messages`：送信者、内容、送信日時、削除状態。
- `board_items`：タスク・決定・質問、提案中か確定済みか。
- `events`：イベント名、日時、場所、人数制限。
- `rsvps`：参加者ごとの回答と変更日時。
- `ai_requests`：AI実行者、対象会話、モデル、使用量。
- `ai_suggestions`：AIが作成した下書き、承認者、変更履歴。

**重要：** 画面のボタンを隠すだけでは安全ではありません。すべての閲覧・編集で、サーバー側がグループへの参加権限を確認します。SNSの連絡先や不参加理由にも別の公開設定が必要です。

## チャットが届く仕組み

1. 送信者のログイン状態とグループ参加権限を確認します。
2. 不適切な入力や大量送信を制限します。
3. メッセージをグループIDと日時とともに保存します。
4. 同じグループの閲覧権限があるメンバーだけに通知します。
5. ブラウザを再接続したときに履歴を復元します。
6. 管理者による招待取り消し、メンバー管理、通報に対応します。

## AIが共有ボードを整理する仕組み

1. 権限のある人がイベントと対象メッセージを選び、AIへの整理を依頼します。
2. 参加者が理解できる形で外部AIへの送信内容と同意条件を示し、許可された範囲だけを処理します。
3. サーバーから必要最小限の会話をAIに送ります。
4. AIがタスク候補、日程案、決定事項の候補、未回答の質問を整理します。
5. 形式を検証し、あいまいな表現や矛盾は未確定として残します。
6. 共有ボードに**下書き**として表示します。
7. 人が確認・修正・承認した項目だけを確定します。
8. 実行した人、使用量、費用、承認履歴を安全に記録します。

例：「土曜なら参加できる」は、「イベントが土曜に決定した」ことではありません。AIが勝手に確定事項へ変更してはいけません。

## AIの費用を抑える方針

**最初は有料APIを利用：** OpenAI API または Anthropic Claude API をサーバーから呼び出します。APIキーをWeb画面や公開コードに置きません。送信する会話を短くし、利用回数、トークン数、月額使用量の上限を設けます。**人が承認できる有用な要約1件あたりの実費**を記録します。

**将来は自前モデルも比較：** 実際の利用量が増えた段階で、ライセンスを確認したオープンウェイトモデルを同じ安全なテスト会話で評価します。誤った決定事項、日本語・英語の品質、応答時間、GPU、メモリ、サーバー代、電気代、アップデート、保守時間を比較します。

**判断方法：** 外部API、自前運用、両方を使う方式の中から、品質と総費用で選びます。ローカルAIは無条件で無料・低コストになるわけではありません。

## 技術の候補

ブラウザ側にはTypeScript系Webアプリ、サーバー側には認証、PostgreSQLなどのデータベース、リアルタイム配信、AI接続機能が必要です。Next.jsやSupabaseは候補ですが、正式には決定していません。保守性、セキュリティ、費用、開発者の経験などを比較して選びます。

## プライバシーと安全性

- グループは原則非公開とし、招待や権限を管理します。
- プロフィールのSNSや連絡方法は任意入力とし、公開範囲を本人が選択します。
- AIがチャットを処理するときは、利用目的・対象範囲・保存期間を明確にします。
- LINEやInstagramの非公開会話履歴を無断取得しません。
- 人の承認なしにAIが連絡・予約・支払い・情報公開を行いません。
- 通報、削除、迷惑行為防止、アクセス制限のテストを用意します。
- 将来の実際の決済は専門事業者を利用し、カード情報をアプリ自身で保存しません。

## 最初の受け入れテスト

2人が安全にチャットでき、履歴が残り、共有タスクが同期すること。第三者には閲覧・変更できないこと。AIのテストでは、同意した会話から下書きを作り、承認するまでは正式な内容に反映されないことを確認します。
