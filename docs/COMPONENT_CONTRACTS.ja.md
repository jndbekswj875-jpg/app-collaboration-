# 共同開発のための機能間インターフェース

[English version](COMPONENT_CONTRACTS.md)

**状況：** 次の開発段階に向けた設計案です。ここに書いたサーバーAPIはまだ実装されていません。

## 目的

友達がチャット画面、共有ボード、バックエンド、AI接続を別々のブランチで開発しても、後から一つのシステムとして組み合わせられるように、データの形式と機能の責任範囲をそろえます。

## 画面が受け取るデータ

- グループ画面：グループID、名前、説明、利用者の役割。
- チャット画面：グループID、メッセージID、送信者ID、本文、送信日時、配信状態。
- 共有ボード：項目ID、タスク・決定・質問の種類、本文、下書き・進行中・完了・確定などの状態。
- AI確認画面：提案内容、参照したメッセージID、不確かな部分、承認・修正・却下の操作。
- イベント画面：イベントID、グループID、日時、場所、定員、本人の出欠回答。

## 将来のサーバー操作

| 操作 | 入力 | 必要な動作 |
| --- | --- | --- |
| グループ一覧 | ログイン済みのセッション | 本人が参加しているグループのみ返す |
| メッセージ取得 | グループID、取得位置 | 所属権限を確認して履歴を取得 |
| メッセージ送信 | グループID、本文、送信リクエストID | 入力を検証して保存、重複送信を防ぐ |
| リアルタイム購読 | グループID、最終受信位置 | 権限を確認し、切断後も復旧する |
| ボード取得 | グループID | 権限がある人だけに表示する |
| ボード更新 | グループID、項目ID、変更内容 | 権限と同時編集の競合を確認する |
| AI下書き作成 | グループID、許可済みの対象メッセージ | 下書きのみ作成し、利用量を制限する |
| AI下書きの確認 | 提案ID、承認・修正・却下 | 権限のある人が確定する |
| 出欠変更 | イベントID、本人の回答 | ログイン本人の回答だけを変更する |

## チケット注文とAI連携のインターフェース案

以下は**将来の設計案**であり、使えるAPIではありません。開発前に権限、二重処理の防止、注文やチケットの状態を確認します。

| 操作 | 入力 | 必要な動作 |
| --- | --- | --- |
| チケット種類を登録 | 主催者、イベントID、価格・通貨・枚数・期間 | イベントの権限がある主催者だけが操作する |
| チケット種類を確認 | イベントID | 閲覧者に公開してよい商品だけを表示する |
| 注文を作る | 購入者、チケット種類、枚数 | 在庫を安全に確保し未払い注文を作る |
| 決済を始める | 注文ID | 外部決済事業者を利用し、秘密情報をブラウザに渡さない |
| 決済通知を検証 | 決済事業者からの検証済み通知 | 重複を防ぎ、確認後にチケットを発行する |
| 自分のチケットを表示 | ログイン済みの購入者 | 本人または許可された人だけに表示する |
| チケットで入場する | イベントID、チケットコード、受付担当者 | 不正・返金済み・使用済みチケットを拒否する |
| 返金を依頼する | 注文・チケットと適切な権限 | 規則に基づき決済と状態を処理・記録する |
| AI下書きを依頼する | 許可済みのイベント情報と同意の範囲 | 要約・タスク・告知文の下書きを返すだけにする |
| 告知を承認して実行 | 主催者が確認した下書き | 通知の同意などを確認した別の操作で送る |

**分けて作る機能：** `groupService`、`eventService`、`messageService`、`ticketOrderService`、`paymentProviderAdapter`、`aiModelAdapter`、`marketingDraftService`。AIは特定の会社のモデルに依存させず、在庫、価格、決済状態を直接変更させません。

**チケットのデータ構造：** イベントとチケットの種類を関連づけ、注文者、金額、通貨、決済状態、固有のチケット番号、入場・返金の状態を適切な権限で保存します。非公開チャットを決済事業者へ不必要に送信しません。

## 安全性の共通ルール

1. 画面から送られたユーザーIDを本人確認の証拠として信用せず、サーバーのログイン情報で確認します。
2. すべての取得・更新・リアルタイム購読で、グループ参加権限を確認します。
3. 画面から送られたグループIDやメッセージIDをそのまま信用しません。
4. 非公開の連絡先や任意の欠席理由を、許可なく他のメンバーに渡しません。
5. AIは許可された会話だけを処理し、提案を勝手に確定したり連絡を送ったりしません。
6. 二重送信、権限エラー、入力エラー、同時編集、利用制限などの動作を定義します。
7. 外部サービス固有の処理は一か所にまとめ、画面全体に直接書き込まないようにします。

## 別々の成果物を統合する方法

担当者は、作業前にGitHub Issueで入力、出力、権限、完成条件を確認します。一つの機能ごとにプルリクエストを作り、テストとレビューを経て統合します。共通の形式を変更する場合は、この資料と関連タスクも同時に更新します。
